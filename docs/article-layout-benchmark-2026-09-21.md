## 2. Bloguito 실제 게시물·현행 코드 대조

2026-09-21 공개 WordPress REST API `/wp-json/wp/v2/posts/{ID}`를 읽기 전용으로 확인했다. 응답 네 건 모두 HTTP 200, 상태 `publish`. `content.rendered`의 HTML 요소 수를 파싱했으며, 숫자는 콘텐츠 사용성 또는 검색 성과의 점수가 아니다.

확인한 구조·원인:

1. 공통 렌더러 `agent-publisher/agents/editorial.py`에는 **요약→행동 박스(확인된 링크가 있을 때)→목차→모든 절에 STEP 배지→FAQ→출처**가 고정되어 있다. `actions`가 없는 출처 URL을 자동 행동 버튼으로 만드는 동작은 현재 코드에서 제거됐지만, #243의 기존 공개 HTML에는 과거 방식의 길고 거의 구별되지 않는 버튼 세 개가 남아 있다. 공개 글은 렌더러 변경만으로 자동 갱신되지 않는다.
2. #243과 #304의 상단 링크가 세 개이고 #349는 네 개다. 행동의 종류·목적지에 따라 한 개의 우선 행동과 필요한 보조 행동을 구별할 여지가 있다. 모든 링크를 일괄 줄이면 공연 지역별 필수 예매 경로를 누락할 수 있으므로 글별로 판단한다.
3. #218은 본문 단계 7개와 FAQ 6개가 있으나 비교표는 없다. 보험회사 보유분과 출연 휴면보험금의 **조회·청구 경로** 등 동시 비교를 표로 제시할 후보이다. 조건·예외·출처를 보존해야 하며 제도 최신성은 별도 재검토한다.
4. #243의 조회와 환급 신청, 온라인 제한 대상, 사업자별 연락처는 현재 문단에 흩어져 있어 스캔 비용이 크다. 조회/신청 비교와 '사이트 조회 제한 → 가입 통신사 문의' 안내표가 후보이다. 실제로 표로 변경하기 전 원문 인용과 사용자 검토가 필요하다.
5. #304는 단일 품목/묶음 수거 기준을 상단 요약에 담았으나 비교표가 없다. 규격·품목 예외가 복잡하고 공식 자료가 충돌할 수 있으므로 **확인 가능한 범위**만 표로 표시하고 추측으로 빈칸을 채우지 않는다.
6. 현재 생성 표 HTML에는 `caption`, `scope="col"`, `scope="row"`, 수평 스크롤 래퍼가 있다. 다만 최소 너비 580px이고 좁은 화면에서 좌우 스크롤 안내는 명시돼 있지 않다. 표가 실제로 잘 보이는지 모바일 360px/390px 및 200% 확대에서 검증해야 한다.
7. 상단 핵심 요약은 실제로 존재하지만 `3초 요약`+`핵심요약`이 동시에 표시된다. 첫 화면에서 사용자 질문에 필요한 구체적인 답·조건·행동이 반복된 시각 요소에 밀릴 수 있다. 요약을 삭제하는 대신 라벨을 하나로 단순화하는 실험을 제안한다.
8. 일반적인 상단 정보 박스가 22px 패딩·36px 아래 간격을 사용하고, FAQ도 전부 카드로 펼쳐져 있다. 장문 글은 위에서 아래로 길어지는 구조다. 기존 데이터에서 실제 이탈/불편은 측정되지 않았으며 작은 화면에서 확인한 뒤 조정한다.
9. 홈페이지의 검색 수집 텍스트에는 요약 라벨·CTA 문구가 목록 요약에 섞여 읽힌다. 실제 목록 화면 캡처와 WordPress excerpt 설정을 확인해 내용 요약 1~2문장만 노출하는지 별도 조사할 필요가 있다.

**중요:** 243·218·349·304의 공개 상태/HTML은 이 조사 시각의 REST 응답이다. 최종 사용성·실제 신청 성공·광고 노출, 렌더링의 시각적 겹침 여부를 확정한 것은 아니다. 위 게시물의 원문 내용 변경이나 교정은 현행 `editorial_cli.py` 검토·원본 해시·백업 경로만 사용한다.

## 3. 권장 정보 구조: 복지·환급 설명 글

상황별 정보 구조를 바꾸되 본문 전체의 조건·출처를 보존한다. 화면이 복잡한 이중 요약, 광고처럼 보이는 반복 CTA, 공식 기관이 아닌 페이지의 공식 사칭 아이콘은 피한다.

```text
게시물 제목: 독자의 구체적인 질문 + 적용 대상/연도(실제로 필요할 때)
작성자/게시 정보: 사실인 이름·수정 시각만 / 적용 기준 연도·지역 표시
┌ 한눈에 답 ─────────────────────────────────────┐
│ 핵심 답 1~2문장 + 중요한 제외·지역 조건(확인된 경우) │
└───────────────────────────────────────────────┘
한눈에 보기: 대상 | 무엇을 받나 | 신청/조회 기간 | 신청 경로
내 상황은? 적용 가능한 경우/적용 안 되는 경우(검증된 분기표)
[해당 제도의 실제 조회/신청 화면으로 이동]  ← 검증된 행동 경로에만
방법: ① 준비 ② 공식 화면의 실제 메뉴 ③ 접수·결과 확인
안 되는 경우: 인증 실패/대리·예외/문의처
필요한 경우에만 FAQ 3~6개(본문 반복 대신 막히는 구체적 질문)
관련 독자 과제 링크 1~2개 · 공식 자료와 적용 연도/기관
```

**형식별 선택 규칙:** 두 개 이상의 선택지를 동일 항목으로 비교하면 표를 검토한다. 한 번 따라 하는 업무는 순서 목록, 자격의 예외·오해는 짧은 상황별 블록, 직접 근거가 필요한 주장에는 정확한 공식 근거 링크를 제공한다. 표가 한두 셀로 끝나면 설명 목록(`dl`)이 오히려 읽기 편할 수 있다. 공연은 일정표, 환급은 조회/신청 차이표, 지원금은 대상·혜택·기간표처럼 데이터의 관계에 맞춰 형태를 선택한다. 모든 주제를 `STEP`으로 통일하지 않는다.

**미리보기 예시(#243의 구조 제안; 게시 원고 아님):**

| 무엇이 궁금한가 | 바로 찾을 곳 |
| --- | --- |
| 가입 없이 조회 가능? | 핵심 답과 `조회하기` 동작 |
| 조회가 제한되는 대상? | 적용 대상·제외 대상 표, 가입 통신사 문의 경로 |
| 환급은 어떻게 신청? | 별도의 로그인·본인 명의 계좌 단계 |
| 입금이 늦으면? | 지급 담당 통신사와 결과 조회 구분 |

## 5. 2주 소규모 사용자 검증 (제안)

1. **기준선:** #243·#218 중 1편을 선택해 현재 HTML을 보존하고 모바일 360/390px 및 데스크톱 화면을 실제로 촬영한다. 빈 화면, 겹치는 박스, 가로 스크롤, 읽기 크기 및 링크 목적지를 확인한다. 방문·수익 데이터가 없다면 미측정으로 기록한다.
2. **테스트 과제:** 사전 정보가 다른 3~5명의 협조자에게 ① 본인 상황에 해당하는지 판단에 필요한 조건 찾기, ② 실제 조회/신청 화면 찾기, ③ 불가능한 경우 문의처 찾기를 준다. 성과는 정답 도달 여부, 걸린 시간, 잘못 해석한 조건과 클릭 경로다. 테스트 인원이 적으므로 대표 모집단으로 일반화하지 않는다.
3. **작은 수정:** 글 하나만 공식 최신 자료 재검토 → 구조화 bundle·독립 검토 → 변경 미리보기 → 기존 공개글 안전 갱신. 해당 글과 주제 특성이 맞는 다른 글을 비교하되 날짜·대상과 유입 채널의 차이 때문에 단순 전후 비교로 인과를 단정하지 않는다.
