# Bloguito 콘텐츠 구조·수요 발굴 실행 설계 (2026-09-20)

> **상태: 편집·제품 전략 제안서.** 이 문서는 사이트 메뉴, WordPress 분류, 기존 글, 자동화 코드, 발행 스케줄을 변경하지 않는다. 실제 배포·편집 정책 적용은 별도 구현·검증이 필요하다. 경쟁 사례는 기능 참고용이며 실측 방문·매출 상위 순위가 아니다. 현재 Bloguito의 유입과 수익이 작아 수요·성과를 확정할 수 없다.
>
> **목적:** 소규모 정보 사이트의 실행 가능한 패턴(지원금 목록/필터, 계산·비교 도구, 질문형 가이드, 관련 글 허브)을 참고하되 텍스트·이미지를 복제하지 않고, 원문 근거와 독자 문제 해결에 집중한다.

## 1. 전략적 선택: 글 모음에서 '생활 행정 문제 해결 안내'로

- 1차 집중: **지원금·복지**와 **세금·환급**. 기존 공식 근거와 문항을 재활용하고, 같은 제도에 관한 분산 문서를 관리하기 쉬운 형태로 묶는 실험이다. 수요나 높은 광고 단가가 입증되었다는 뜻이 아니다.
- 2차: **생활·건강** 중 민원 절차·공식 조회처럼 좁고 검증 가능한 질문. 의학적 치료 조언, 수익·환급 확정, 신체 건강을 보장하는 표현을 배제한다.
- **공연·콘서트**는 기존 카테고리로 유지하되 당분간 신규 투자를 가설 단계로 두고, 잔여 판매기간·정확한 회차·공식 상품 URL·현재 판매상태를 검증하지 못하면 보류한다. 카테고리 폐지나 코드상의 자동화 중단은 이번 문서에 포함되지 않는다.
- 60% 상시 / 40% 시즌형은 기존 편집 정책의 목표값이지 실제 달성치가 아니다. 실제 수요·검증 부담·정보 유효 수명을 고려해 편집 회의에서 조정한다. 코드 정책의 `min_remaining_days=30`은 그대로 유지한다.

### 제안 정보 구조 (현재 구현 아님)

```text
생활정보 24 홈
├── 지원금·복지 [기존 welfare: 표면명/허브 개편 제안]
│   ├── 제도별 대표 안내(1개 URL)
│   ├── 대상/조건/예외/신청방법/잔액·결과조회 질문형 하위 글
│   └── 지원 대상별 '찾아보기' 필터 (후속 MVP)
├── 세금·환급 [기존 tax]
│   ├── 현금 환급 / 세액공제 / 포인트 혜택을 명시적으로 구분
│   ├── 제도별 대표 안내와 질문형 글
│   └── 검증 가능한 단순 계산·비교 도구 (후속 MVP)
├── 생활·건강 [기존 life-health]
│   └── 여권·보건 민원 등 공적 절차/조회 중심; 의료 판단은 제외
├── 공연·콘서트 [기존 concert 유지; 일정 유효성 엄격 적용]
└── 공통 진입 화면 (향후)
    ├── 신청 일정: 신청/사용/지급 날짜 분리, 종료 상태 표시
    ├── 계산·비교: 전제·적용 연도·산식 공개, 결과는 참고용
    └── 제도별 탐색: 대상·상황별 필터와 공식 사이트 이동
```

**기존 4개 WordPress 카테고리의 키·ID는 그대로 둔다.** 필터와 계산기는 이 문서에서 제안한 제품 아이디어일 뿐, 구현 또는 정확도가 확인된 기능이 아니다. 실제 추가 시 계산 결과를 수급 판정이나 지급액으로 표시하지 않는다. 먼저 사람 검토 체크리스트/표로 검증한 다음 코드화한다.

### URL 및 내부 링크 원칙

1. 한 제도·연도·주요 질문군에 대표 허브 URL을 지정한다. 최신 기준·시행 연도·최종 근거 검토일·원문 개정일(확인 가능할 때)을 표시한다.
2. 하위 문서는 **독립적인 해결 과제**가 있는 경우만 생성한다. 예: 신청 방법, 재신청 시 변경 신고, 잔액조회. 대표 허브의 같은 기준표·서론을 복사하지 않는다.
3. 기존 URL은 곧바로 삭제하거나 리디렉션하지 않는다. 중복 여부, 실제 검색 의도, 인바운드 링크, 유지보수 난이도를 검토한 뒤 통합·갱신·유지 중 결정한다. 필요하면 301과 내부 링크, 검색 색인 영향을 별도로 검증한다.
4. 각 하위 글 상단에는 허브 이동, 하단에는 '다음에 할 일' 성격의 연결 글 1~3개를 놓되 독자의 과제와 직접 관련될 때만 링크한다. 외부 공식 링크는 출처와 신청 경로를 구분한다.
5. 본문이 갱신되는 경우 중복 글의 구버전 수치도 찾아 함께 점검한다. 지난 기준을 정정 이력으로 인용할 때는 현재 기준과 시각적으로 분리한다.

## 2. 초기 트래픽이 없어도 수요를 발굴하는 과정

**관찰 신호와 검증하지 않은 가설을 혼동하지 않는다.** 한 사이트의 게시글 수, 경쟁사의 모방, 자동완성 노출, 검색 결과의 존재는 '높은 검색량' 또는 결제 의향의 증거가 아니다.

| 자료 | 얻을 수 있는 증거 | 말하면 안 되는 결론 |
|---|---|---|
| 공공기관 FAQ/상담 안내·개정 공고 | 공식적으로 설명하는 질문과 헷갈리기 쉬운 조건 | FAQ 1개 = 월 검색량 또는 독자 불만 규모 |
| 공개 커뮤니티/게시판·앱 리뷰 | 실제 질문의 표현, 막힌 단계, 답을 찾지 못한 맥락 | 일부 댓글 = 전체 이용자 대표 표본 |
| Google/네이버 검색 결과 수동 관찰 | 어떤 의도를 다루는 글이 있는지, 최신성·조건·지역·원문 링크의 결손 | 검색 결과 개수 = 키워드 수요/난이도 |
| Google Trends / 네이버 데이터랩 | 설정한 지역·기간의 상대 관심 변화, 시기별 패턴 | Trends 0 = 수요 0; 지수 = 절대 월 검색량 |
| Search Console(추후) | 자사 사이트 실제 노출·클릭·질의, 페이지별 CTR | 소량 노출의 변동 = 유의미한 시장 크기 증명 |
| 간단한 사용자 과제 테스트 | 정해진 조건의 사람이 답을 찾았는지, 막힌 지점 | 5명의 피드백 = 시장 전체의 반응 |

- **자료 수집:** 후보 주제 20개를 모은다. 각 주제의 공개 질문 링크/날짜/문구(개인정보 제외), 최신 공식 URL, 현재 검색 결과의 설명 공백, 기존 Bloguito 관련 URL을 기록한다. 질문 인용은 짧게 요약하고 개인 계정·댓글 데이터를 저장하지 않는다.
- **독립적 신호:** 동일 게시물의 재인용은 1건으로 센다. 서로 다른 출처에서 비슷한 질문을 보거나 공식 FAQ + 독립적인 공개 질문이 있으면 추가 검토 후보로 삼는다. 이것도 실제 시장 규모의 증거는 아니다.
- **SERP 공백 수동 점검:** 검색어/날짜/기기/검색 환경을 기록하고, 상위 노출 문서 5~10개에서 [정확한 대상, 적용 연도, 조건/제외, 절차, 직접 링크, 수정 이력, 사용 가능한 예시]를 체크한다. 공식 자료가 이미 충분하면 새 글보다는 기존 글 업데이트 또는 다른 질문을 고려한다. 타사의 표현·표·이미지는 복제하지 않는다.
- **시계열:** Google Trends는 검색의 표본을 0~100으로 정규화하며, 검색량이 적은 용어는 0으로 나타날 수 있다. 네이버 데이터랩 역시 지표와 설정 범위를 확인해 상대적 비교에만 사용한다. 숫자나 유입 추정치를 만들지 않는다.
- **수요 후보 기록:** `후보/실제 질문/질문 근거 URL·시각/공식 원문·버전/다른 문서의 공백/중복 URL/유효 종료일/검증 난도/독자 과제/확인해야 할 미지수/결정(검토·보류·갱신·초안)` 항목을 필수로 둔다.

## 3. 원고 1편의 품질 기준: 정보가 아니라 과제 해결

다음은 **사람이 검토할 편집 기준**이다. 아래의 독립 재검색·사용성 검사는 현행 자동 `validate_bundle()`이 완전히 구현한 기능이라고 간주하지 않는다. 현행 코드의 검사와 최종 사람 검토는 둘 다 요구한다.

**발행을 보류하는 필수 조건 (하나라도 미충족):**

- **질문·범위:** 제목에 있는 질문을 첫 단락에서 직접 답했는가? 대상·연도·지역과 이 글에 포함하지 않는 경우를 분리했는가?
- **최신 공식 근거:** `fetched_at` 외에 **자료 발행/개정일·실제 시행일·적용 연도·대상 코호트**를 따로 대조했는가? 같은 기관의 더 최신 공고 또는 정오표가 없는가? 서로 충돌하면 보류했는가?
- **주장 장부:** 제목, 요약, 본문, 표, FAQ, 예시의 핵심 수치/날짜/단위/자격/제외/경로마다 `주장 → 원문 URL → 해당 원문 위치/발췌 → 적용 연도 → 판정`을 확인했는가? 해시·동일 인용만으로 참으로 간주하지 않았는가?
- **오해 방지:** 현금 환급과 비현금 혜택, 신청/사용/지급 시점, 수급 선정 기준과 최대 지급액, 추정과 확정을 구분했는가? 결과를 보장하지 않는 것에서 그치지 않고 실제 예외를 설명했는가?
- **실제 실행 가능:** 공식 신청 URL이 해당 질문의 올바른 화면으로 이동하는가? 안내한 메뉴를 재현했는가? 로그인이 필요한 화면은 공개 페이지에서 확인 가능한 부분과 미검증 부분을 구분했는가?
- **차별성:** 기존 대표 글과 중복하지 않으며, 독자에게 새로운 상황별 분기·정확한 계산 전제·누락된 예외·신청 체크리스트 중 하나 이상 제공하는가?
- **검토·공개:** 원고 생성 모델과 별도로 사람이 공식 최신 원문을 검색·대조했는가? 현행 bundle 필수 검사와 만료 검사 및 명시적인 공개 승인까지 거쳤는가?

**권장되는 읽기 구조:**

1. 첫 화면: 질문에 대한 한 문장 답 + 누구에게 적용되는지 + 해당 연도.
2. '나는 어느 경우인가?' 상황별 분기표(기계가 판정하는 듯한 표현 금지).
3. 실제 준비물·신청/조회 단계(확인된 버튼·메뉴만).
4. 실패/예외: 대리 신청, 정보 변경, 사전·사후 지급 등 질문에 직접 필요한 예외만.
5. 사람 기준으로 검산 가능한 예시(전제, 산식, 적용연도; 확인 안 된 예시는 넣지 않음).
6. 다음 행동: 검증한 공식 바로가기, 연관 질문, 연락할 기관, 출처와 변경 이력.

**피할 관행:** 동일 내용 3개 URL 반복, '전 국민 100%/즉시/1분/무조건' 보장, 미확인 가격·최저가, 글자 수 채우기, 요약을 요약하는 FAQ, 매 문단 무관한 버튼, 출처 없는 AI 이미지로 기관/혜택을 공식처럼 묘사하기.

## 4. 첫 번째 파일럿: 2026년 에너지바우처 '상황 해결' 클러스터

**선정 이유는 검증 가능한 질문 분기가 많다는 편집 판단**이다. 대규모 검색 수요는 측정하지 않았다. 현재 공식 사이트는 자동·신규·재신청, 신청/사용기간, 잔액조회 화면을 각각 설명한다. 특히 과거 2015년 등록 FAQ가 2025년 지원기간을 안내하는 경우도 있어 자료의 URL이나 조회 시각만으로 2026년 기준을 판정하지 말아야 한다.

| 하위 글: 에너지바우처 잔액이 보이지 않으면? | 로그인·메뉴·사용기간·상담 경로 확인 | https://www.energyv.or.kr/info/balance_inquiry.do | 로그인 후 실제 UI는 테스트 여부 표시, 계정정보 수집 금지 |
| 소형 도구 후보: 신청 전 체크리스트 | 내 상황에서 확인할 서류·변동 사항 정리 | 위 공식 신청 안내 | 초기에는 읽기 전용 체크리스트, 서버에 민감정보 저장 금지; 효과 확인 전 계산기 제작 금지 |

**범위 제약:** 에너지바우처 지원 대상 또는 개인별 금액을 대신 확정하지 않는다. 공식 홈페이지에 수치가 있어도 2026년 적용분·변동 시각을 검토하지 못했다면 해당 수치를 신규 글에 넣지 않는다. 공식 페이지의 과거 FAQ 내용과 최신 사업연도 내용을 합쳐 단정하지 않는다. 세 글의 질문이 실제로 독립적이지 않다면 허브 내 섹션으로 합치고 새 URL을 만들지 않는다.

### 두 번째 검증 후보 (수요 미측정)

- **세금포인트:** 포인트 혜택과 현금 환급을 혼동하지 않고, 2025년 이후 부여분의 적용 규칙과 실제 사용 메뉴를 명확하게 설명. 최근 오류 정정 이력이 있으므로 공식 최신 자료·코호트 재검증 후에만 착수.
- **본인부담상한제:** 어느 진료 연도에 발생한 본인부담금인지, 사전급여/사후환급의 차이, 제외 항목, 본인 계좌가 아닌 경우 필요 서류를 분리. 국민건강보험공단 공식 안내를 먼저 검토하고 당해 연도 상한액 추정표는 작성하지 않는다.
- **여권 온라인 재발급 수령:** 국내 수령의 준비물·본인 방문·예외 상황·기관 변경 가능 여부를 분리. 정부/여권 공식 페이지로 절차 갱신을 확인한다.

이 후보들은 검색량·소득 전망·검색 순위가 입증된 '히트 키워드'가 아니다. 초기 편집 작업의 구체적인 검증 대상이다.

## 5. 2주 실험: 트래픽 대신 해결 능력을 먼저 검증

| 기간 | 작업 | 남기는 증거 |
|---|---|---|
| 1~2일 | 20개 후보 질문 수집, 공식 근거/검색 결과/기존 URL 비교 | 날짜와 URL이 있는 후보 장부, 제외 이유 |
| 3~4일 | 에너지바우처 대표 허브 1편과 하위 질문 최대 2편의 원고 작성, 모든 핵심 주장 장부 작성 | 원문 스냅샷, 버전·조건 대조표, 누락 목록 |
| 5~6일 | 2차 공식 독립 검색과 사람이 직접 신청 경로/문구 검증. 오류가 있으면 초안 유지 | 독립 검토 메모와 수정 전후 차이 |
| 7~9일 | 독자가 직접 해 보는 3개 과제(자동신청 판단에 필요한 정보 찾기/잔액 메뉴 찾기/신청·사용기간 구분) | 수행 성공/실패, 클릭 경로, 오해한 문장; 개인정보 수집 금지 |
| 10~11일 | 겹치는 문서는 통합, 글 사이 연결·모바일 가독성 점검, 기존 콘텐츠와 충돌값 재검색 | 변경 목록과 미해결 사항 |
| 12~14일 | 사용자 승인 후 공개 여부 결정; Search Console 페이지·질의·색인 상태는 가능한 범위에서 기록 | 관측값과 미측정값 분리한 실험 기록 |

**사전 성공/보류 기준(사업 성과 예측값 아님):** 모든 중요 주장이 공식 최신 근거와 일치하고(필수), 새 글이 다른 질문을 해결하며(필수), 소수의 과제 테스트에서 반복되는 막힘을 식별·수정할 수 있을 것. 오류를 수정할 수 없거나 공식 원문이 충돌하면 공개 보류. 2주간 PV/클릭이 0이어도 수요 없음이라고 판정하지 않는다. 게시 후 28일·56일의 유입을 탐색하되 표본이 부족하면 '판단 보류'로 기록한다.

**측정 장부 예시:** 페이지 URL/발행일/공식 근거 개정일/검토일/노출/클릭/CTR(소량 분모 주의)/색인 상태/독자 과제 테스트 건수/성공·실패/오류 제보/편집 시간/광고 활성화 여부/실제 확인한 광고 수익. 검색량·경쟁사 매출·자체 RPM은 실제 측정하지 않았으면 `미측정`으로 둔다.

## 6. 편집·개발 백로그와 변경 범위

**문서화만으로 즉시 가능한 것:** 후보/주장/버전 장부, 원고 템플릿, 중복 URL 지도, 공식 원문 두 번 대조, 3개 과제 테스트, 기존 글 정정 이력 추가. 사람이 확인하는 운영 절차다.

**코드 작업이 필요한 것(현재 미구현):** 허브용 WordPress 템플릿·탐색 메뉴, 자동 관련글 매핑, 공식 공고 개정 감지와 검증 기한 알림, 분기별 필터, 개인정보 미저장 계산기, Search Console 연동, 통합·301 자동화. 초기에는 공고 개정 감지가 완전 자동 최신성 보장이 되지 않는다는 점을 명시한다.

**기존 운영과 연결:** `agent-publisher/editorial_policy.json` 및 `docs/EDITORIAL_SYSTEM.md`의 현행 원문 근거·만료·검토·draft 게이트는 그대로 적용한다. `agents/critical_facts.py`는 발견된 일부 오류 패턴만 차단한다. 이 문서의 신규 편집 항목을 코드가 통과시켰다고 주장하지 않는다. 검증된 초안을 사람의 명시적 승인 없이 공개하지 않는다.

## 7. 의사결정 체크포인트

- **2주 후:** 실제 질문/공식 근거/독자 수행 결과가 확보됐는가? 불명확하면 새 카테고리나 계산기 개발에 투자하지 않는다.
- **4~8주 후:** 검색 색인과 노출이 관측되는가? 노출과 클릭이 적으면 제목 변경만 반복하지 않고 기술적 색인·검색 의도·원문 가치·검색 환경을 점검한다.
- **12주 후:** 콘텐츠 갱신·오류 수정에 드는 시간이 지속 가능한가? 콘텐츠 생산량보다 정확성·독자 과제 해결률·재검토 가능성을 먼저 본다. 광고 매출 수치가 실제로 발생한 경우에만 수익화 판단에 사용한다.
