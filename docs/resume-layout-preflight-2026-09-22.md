## 목차·상자·표 실제 설치의 구체적인 안전 조건

1. 설치 범위와 현재 대상 ID를 다시 확정한다. 이전 목차 계획의 '19편 변경/11편 무변경'은 구형 #137이 포함된 당시 결과다. #137의 새 구조는 자체 목차를 갖추고 있으므로 현재 설치 시 이 파일의 `bloguito-article` 배제에 의해 출력 무변경이어야 한다. 현재 REST 30편에 로컬 TOC/표 필터를 재적용한 전체 전후 비교로 예상 변경 ID를 새로 기록하고, 사용자에게 승인된 범위와 정확히 일치시키며 기타 글은 무변경을 증명한다. 한 글이라도 예상 밖이면 설치를 중단한다.
2. 설치 바로 전 운영 MU 전체 목록·기존 두 파일 SHA·새 파일명의 부재, 캐시/활성 플러그인, 공개 원고·#85 저장 및 출력 해시, v3 백업 무결성·복구 절차를 다시 확인한다. #85 플러그인은 전체 본문 해시가 네 가지 허용값 중 하나가 아닐 경우 출력에 적용되지 않으므로, 해당 지문을 읽어 재확인하고 변경 원문을 억지로 허용목록에 추가하지 않는다. 기존 MU 파일과 무관한 작업자의 미커밋 파일은 보존한다.
3. 승인된 **한 개 MU 파일씩** 전송한다. 현재 `wordpress/setup.sh`는 글 삭제·테마/플러그인 변경을 수행하는 초기화 스크립트여서 금지하고, `scripts/install_editorial_release.py`는 에디토리얼 Python/doc 설치기여서 MU 배포에 사용하지 않는다. 공개 HTML과 연결된 PHP 파일의 해시를 확인하고, 대상 디렉터리에서 PHP로 인식되지 않는 임시 확장자 파일로 스테이징 → SHA·PHP 문법 재검사 → 기존 대상 파일 미존재를 재확인 → 승인된 파일명으로 이동하는 단일 파일 설치만 사용한다. 단순히 Docker Compose를 재생성하거나 전체 백업을 복원하지 않는다.
4. 하나의 MU 설치 직후 실제 비로그인 URL에서 캐시 상태를 확인해 360/390/1280 CSS 근사·가능하면 네이티브 200%·키보드·전체 스크롤/앵커를 점검한다. 목차는 중복 0, 대상 앵커 1:1, 새 #137 및 기존 다섯 새 구조 글 보존; CSS는 구형 박스에만 작동하고 다른 신규 요약은 불변; #85 표는 두 개의 caption/scope/region/모바일 수평 이동을 각각 확인한다. 서버 원본 `post_content` 및 다른 글 상태/해시가 설치 과정에서 바뀌지 않았는지도 별도 검사한다. 캐시 미반영과 플러그인 자체 실패를 구별한다.
5. 실패하면 새로 설치된 **해당 단일 파일의 현재 SHA가 승인 배포 해시와 일치할 때만** 그 파일만 제거하는 승인된 롤백을 수행한다. 기존 `bloguito-post-id-column.php`, `bloguito-social-share.php`, DB, 다른 레이아웃 파일과 캐시 설정은 건드리지 않는다. 예기치 않은 내용 변경/다른 사람이 덮어쓴 파일이면 강제 제거를 중단하고 상태를 다시 조사한다. 설치 전후 및 롤백 결과를 별도 운영 기록으로 남긴다.

## 반복 감사: 현재 배포 차단과 실행 가능 위치

- 실제 Ubuntu 사용자 `crontab -l`에는 **04:00 백업**과 **08:00 초안 자동화** 두 항목만 있으며 별도 공개 글 감사 항목이 없다. `sudo crontab -l`에서는 root crontab 없음. Windows Task Scheduler에서 이름/경로에 `bloguito` 또는 `legacy audit`가 포함된 항목은 검색 결과 0건이다. 다른 사용자·다른 이름의 모든 스케줄을 전수 확인했다고 볼 수는 없다.
- 서버 `/home/ubuntu/scripts/audit_legacy_posts.py`는 현재 **없다**(read-only `test -f` 결과 1). 로컬 Windows 프로젝트에는 스크립트·`.venv`가 있어 현재 드라이런 가능하므로 스케줄의 설치 장소를 우선 결정해야 한다. 서버 cron을 쓰려면 코드·Python 종속성의 별도 검증된 배포가 먼저 필요하며 단순 crontab 한 줄 추가만으로 작동하지 않는다. `scripts/install_editorial_release.py`로 이 감사 도구를 배포할 수 있다는 근거도 없다.
- 반복 감사는 한 번 실행 후 종료하는 `scripts/audit_legacy_posts.py --recurring-state-dir <전용 상태 경로> --expected-hours 24 --retain 14 --strict-alert` 형태다. `--dry-run`만 읽기 전용이고 일반 반복 실행은 **로컬 상태 폴더·잠금·스냅샷을 생성·정리**한다. WP 공개 REST만 읽지만 출력 경로는 쓰기 가능해야 한다. 사용자 승인된 실행 호스트·빈 전용 폴더와 보관 권한·주기/시작 시간·종료 코드 `0 정상 / 2 검토 필요 / 3 실패`를 수집하는 감독기·미실행 감지/경고 수신자·사람 검토 레지스터 작성자가 아직 확정되지 않았다. 단순 실행만으로 이메일/메신저를 보내는 구현도 없다. 따라서 **운영 스케줄 등록/최초 상태 저장 실행은 아직 진행하지 않았다**.

## 작업 범위와 남은 검증

이번에 새로 작성한 파일은 이 보고서 한 개다. 브라우저는 기존 격리 프로필 재사용으로 단일 프로세스를 켠 상태이며 prime의 추가 QA에 재사용할 수 있다. 세 PHP 소스 모두 운영 PHP에서 stdin 문법 검사 통과, 공개 #137 Edge 세 화면 검사 통과, 공개 REST 감사 드라이런 통과. 로컬 계약 테스트의 최근 30편 대상 수 재검증, MU 플러그인 운영 설치/운영 결합 시각 검사, 최신 백업 무결성/격리 복구, 실제 200% 확대·스크린리더, scheduler 실사용·알림은 **미실시**. 이 보고서의 제안은 적용 명령이나 설치 완료 증빙이 아니다.
