## 공통 CLI 결과와 해결이 필요한 구현 제약

- `build_pilot.py`로 `validate_bundle(bundle, public_only_inventory, require_review=False)` 실행: `status=needs_review`, 사유는 **`availability_not_verified`, `temporal_source_not_bound` 두 개**. 원문 인용 누락 및 문단 수치 미대응 오류는 현재 준비 원고에서 검출되지 않았다. 실제 `editorial_cli.py check bundle.unreviewed.json --inventory public-only-inventory-excluding-137.json` 실행은 종료 코드 **2**, 위 두 사유와 독립 검토 미실행에 따른 `review_not_bound_to_current_content`, `review_stale`, `semantic_review_failed`를 반환했다.
- 원인 확인: 세 국세청 공식 원문은 신청 날짜를 실제로 서술하거나 표로 제공하지만 `agents/temporal_validation.py::extract_evidence()`가 찾는 `신청기간:` 등 *콜론이 있는 라벨* 형식이 아니다. 세 출처의 추출 결과는 모두 빈 배열이다. 현재 시점에는 9월 상반기 신청이 종료됐고 2027년 다음 신청은 아직 시작되지 않았으므로, 기존의 `validate_availability()`에서 진행 중 신청 하나를 요구하는 규칙만으로는 **종료된 신청과 이후 구제 경로를 설명하는 기존 공개 글**을 자연스럽게 검증할 수 없다.
- 독립 모델 검토는 공통 CLI `review`가 사전검사를 통과해야 실행할 수 있으므로 **실행하지 않았다**. API 호출 성공이나 6개 의미검토 항목 통과를 주장하지 않는다. `preview.UNREVIEWED.html`은 CLI가 발급한 검토 완료 미리보기가 아니다.
- 향후 구현 제안(이번 승인 범위 외): *기존 게시물 업데이트 전용* 유효기간 판단에서 공식 원문이 밝힌 `종료된 2026년 상반기 접수`와 `미신청자의 2027년 후속 접수/기한후 신청`을 서로 다른 날짜 필드로 모델링하고, 최신 공식 원문에서 각각의 연도·기간·대상과 FAQ 인용이 결합됐는지 검증하도록 해야 한다. 원문 날짜 표와 자연어를 파싱하지 못하면 명시적으로 `needs_review` 처리하고 사람이 근거를 대조하는 경로를 제공할 수 있다. 신규 게시물의 30일 잔여 유효기간 원칙, 미개시 신청을 접수 중으로 표시하지 않는 원칙, 독립 의미 검토와 출처 재조회 해시 검사는 유지한다. 원고·출처를 임의의 `신청기간:` 증거로 변조하거나 검사를 우회하지 않는다.
